# Open UI + Langgraph Runbook (Frontend Side)

## OpenUI Lang

자체 컴포넌트로 인터페이스를 기술하는 선언형 DSL. 
- JSON 기반 포맷 대비 절반 미만의 토큰으로 모델 생성이 가능하며, 스트리밍에 맞춰 렌더러가 점진적으로 화면을 표시한다.  
- 써야하는 이유 - 1. JSON 기반 대비 토큰 67% 감소 2. Streaming 가능한 언어가 필요했다. ( 호이스팅 허용 -> 점진적 렌더링 허용 )

## Open UI - system prompt  

모델에게 주는 시스템 프롬프트이다. openui-lang의 전용 문법으로 모델이 응답을 하도록 지시한다.  
- 주요 내용 : openui-lang 문법 코드로 응답 지시 + component catalog 정보 주입.  
- ui에서 사용하는 컴포넌트 요소들은 frontend side에 있으니까.pnpm generate 명령어로 시스템 프롬프트를 만들어야 한다.  
  - system-prompt.txt: 모델에게 전달할 프롬프트 (이미 spec.json 포함된 설명)
  - system-prompt.spec.json: 컴포넌트 구조와 타입 명세  

system-prompt.spec.json : Open UI 컴포넌트 입력 규격을 명세한다.  
- root : 최상위 컴포넌트 이름 
- components : 82개의 컴포넌트, 호출 형식(signature)과 설명(description)있음.  
- componentGroups : 82개 컴포넌트를 묶는 상위 그룹이다. 예를들어 에이아웃에서는 Stack, Tabs, TabItem, Accordion 등을 사용해라. 10개의 그룹으로 되어 있다. 
  - 레이아웃, 콘텐츠, 테이블, 차트, 폼, 버튼, 데이터 표현, 카드  


## UI 컴포넌트 카탈로그와 langgraph system prompt sync방법

LLM이 생성할 OpenUI 컴포넌트를 추가하거나 이름·인자·사용 규칙을 변경하면, 프런트엔드 렌더링 카탈로그와 백엔드 시스템 프롬프트를 함께 갱신해야 한다.  

현재 방식: 생성 후 명시적으로 복사  
- 1. 새 컴포넌트 구현과 명세를 OpenUI 라이브러리에 등록하고, 실제 렌더러의 지원도 확인한다. 생성용 export가 같은 카탈로그 일치하도록 맞춘다. 
- 2. `frontend`에서 프롬프트를 생성하고 백엔드 자산으로 복사한다.
- 3. 변경된 프롬프트에 새 컴포넌트의 이름·인자·규칙이 포함됐는지 확인한다. 

```text
[Frontend: 카탈로그 SSOT]
├── components (React UI 컴포넌트)
├── defineFunction() (사용자 정의 계산 함수)
└── defineAction() (사용자 정의 버튼 액션)
      │
      ▼ (npm run generate)
[빌드 타임 프롬프트 생성 (@openuidev/cli)]
├── src/generated/spec.json (컴포넌트/함수 메타데이터 스펙)
└── src/generated/system-prompt.txt (순수 openui-lang 지침 텍스트)
      │
      ▼ (명시적 파일 복사: cp)
[Python LangGraph 백엔드]
└── backend-langgraph/agent/system-prompt.txt
      │  + 런타임 추가 지시문 (도구 설명, Mock 데이터 안내)
      ▼
[create_deep_agent()] ──► [LLM (OpenAI)]
                               │ (openui-lang 코드 생성)
                               ▼
                    [브라우저 OpenUI 런타임]
                    ├── React 컴포넌트 렌더링
                    └── 클라이언트 fn 로직 직접 실행
```

## defineFunction과 defineAction  

- defineFunction : 순수 함수 정의  
- defineAction : 사이드 이펙(부수 효과) 함수 정의  


defineFunction 예제 
```ts

import { defineFunction } from "@openuidev/react-lang";
import { openuiLibrary, openuiPromptOptions } from "@openuidev/react-ui/genui-lib";
import { z } from "zod/v4";

const DiscountPrice = defineFunction({
  name: "DiscountPrice",
  description: "가격에 할인율(0~100%)을 적용한 금액",
  params: z.object({
    price: z.number(),
    discountPercent: z.number().min(0).max(100),
  }),
  returns: z.number(),
  fn: ({ price, discountPercent }) => price * (1 - discountPercent / 100),
});

export const library = openuiLibrary.extend({
  functions: { add: [DiscountPrice] },
});
export const promptOptions = openuiPromptOptions;
```

- Label : 버턴에 표시할 텍스트  
- Action : 액션으로 해석할 수 있는 표현식이 들어간다.

```tsx
// 컴포넌트 정의 
// Actions
export const Button = defineComponent({
  name: "Button",
  props: z.object({
    label: z.string(),
    action: action().optional(),
    variant: z.enum(["solid", "outline", "soft", "ghost"]).optional(),
    color: z.enum(["primary", "danger", "success"]).optional(),
    size: z.enum(["sm", "md", "lg"]).optional(),
    icon: z.string().optional(),
    disabled: z.boolean().optional(),
    block: z.boolean().optional(),
  }),
  description: "icon is a lucide name.",
  component: ({ props }) => {
    // useRunAction()은 컴포넌트의 클릭을 OpenUI 런타임의 액션 실행기로 연결하는 래퍼 훅입니다
    const run = useRunAction();
    const streaming = useIsStreaming(); // 스트리밍 동안 disabled 처리  
    const label = String(props.label ?? "");
    return (
      <button
        type="button"
        className={cx(
          "iui-button",
          `iui-button-${props.variant ?? "solid"}`,
          props.color && props.color !== "primary" && `iui-button-${props.color}`,
          `iui-button-${props.size ?? "md"}`,
          props.block && "iui-block",
        )}
        disabled={!!props.disabled || streaming}
        onClick={() => run(label, props.action, true)}
      >
        {props.icon ? <Glyph name={props.icon} size={props.size === "sm" ? 14 : 16} /> : null}
        {label}
      </button>
    );
  },
});
---
/* 컴포넌트의 클릭을 OpenUI 런타임 액션 실행기에 연결합니다. */
function useRunAction() {
  // Renderer의 React Context에서 액션 실행 함수를 가져옵니다.
  const trigger = useTriggerAction();
  // 가장 가까운 부모 Form의 식별자를 가져옵니다. Form 밖에서는 undefined입니다. 실행기는 이 식별자로 이벤트에 포함할 폼 데이터의 범위를 선택합니다.
  const formName = useFormName();
  // message: 버튼 라벨 등의 요청 문장, plan: DSL에서 해석된 액션 계획,
  // sendLabel: plan이 없을 때 message를 후속 대화 요청으로 보낼지 여부입니다.
  return (message: string, plan: unknown, sendLabel: boolean) => {
    // 액션이 있으면 해당 계획을 실행합니다. 
    // Set 안의 계산식도( 예를들어, Button("실행", @Set($result, @Pick(["A","B","C"]))) 의 Pick) 실제 클릭 시점에 평가됩니다.
    // void는 반환 Promise를 여기서 기다리지 않는다는 뜻이며, 실행 자체는 즉시 요청
    if (plan) void trigger(message, formName, plan as Plan);

    // 액션이 없고 sendLabel=true이면 라벨을 대화 이벤트로 전달합니다. 실제 모델 호출은 호스트가 결정합니다.
    else if (sendLabel) void trigger(message, formName);
  };
}
---
// trigger("실행", "formName" , @Pick(["A","B","C"] )
Button("실행", @Set($result, @Pick(["A","B","C"])))
```

## AgentInterface  

AgentInterface : 풀스택 챗봇 애플리케이션 화면 전체(All-in-one Shell)"를 통째로 제공하는 최상위 컴포넌트  
- 사이드바 (Sidebar) : 이전 대화 목록 (Thread History 히스토리 브라우징) + 새 대화 시작 버튼 (New Chat) + 테마 모드 토글 (라이트/다크)  
- 환영 화면 (Welcome Screen) : 서비스 이름/로고 + 대화 시작 추천 칩/카드 (starters)   
- 채팅 스레드 영역 (Chat Thread Area) : 사용자 메시지와 에이전트 답변 말풍선 + 도구 실행 상태 렌더러 (Tool Call 타임라인/카드) + openui-lang 코드를 컴포넌트(openuiLibrary)로 변환하여 보여주는 생성형 UI 영역   
- 입력창 영역 (Composer):   텍스트 입력창, 전송 버튼, 중단(Stop) 버튼
- 아티팩트(Artifact) 패널 분할 뷰

## Compound Component + Slot 패턴

- `AgentInterface.ThreadHeader`, `AgentInterface.SidebarFooter`처럼 관련 컴포넌트를 부모 API 아래에 묶어 조합하는 방식은 **Compound Component(복합 컴포넌트) 패턴**이다. 
- 이 앱의 OpenUI 구현은 전달받은 자식을 정해진 화면 영역에 배치하는 **Slot 패턴**을 함께 사용한다.

장점 : AgentInterface 을 사용하면 그냥 UI가 뚝딱 나온다. 하지만 특정 부분(예를들어 footer 영역)을 내가 원하는 Ui로 변경하고 싶으면 `AgentInterface.SidebarFooter`을 정의해서 AgentInterface children으로 넣으면 된다.  
- 기본값은 AgentInterface에서 주는 컴포넌트를 사용한다. 커스텀 Ui를 넣으면 그 컴포넌트로 overriding 된다.
- Compound Component 패턴을 사용하므로 'AgentInterface.ThreadList'의 props는 주입받게 된다. 
- Slot 패턴을 사용하므로 Layout은 내가 수정할 수 없다.  

```tsx
<AgentInterface llm={llm} componentLibrary={library}>
  {/* AgentInterface.ThreadHeader override 하는 컴포넌트 */}
  <AgentInterface.ThreadHeader
    showChatTitle={false}
    end={<ReportDocumentInput />}
  />
  <AgentInterface.SidebarFooter>
    <AgentInterface.ThemeModeToggle mode={mode} onModeChange={setPreference} />
  </AgentInterface.SidebarFooter>
  <SaveMessages />
</AgentInterface>
```


Process:
```tsx
// 1. 관련 컴포넌트를 부모 API에 노출한다.
AgentInterface.ThreadHeader = ThreadHeader;

// 2. 컴포넌트 타입과 슬롯 이름을 연결한다.
const SLOT_KEY_BY_TYPE = new Map([
  // key - 같은 함수 객체를 가리키는가?”라는 점에서 포인터와 비슷하게 이해하면 됩니다.  
  [ThreadHeader, "threadHeader"],
  [SidebarFooter, "sidebarFooter"],
  // 나머지 슬롯 생략
]);

// 3. children에서 등록된 타입을 찾아 슬롯으로 분류한다.
const slots = useMemo(() => extractSlots(children), [children]);

// extractSlots 내부 핵심: 유효한 React 요소인지 확인한 뒤 실행한다.
const key = SLOT_KEY_BY_TYPE.get(child.type);
if (key) {
  // 실제 구현은 중복 슬롯이면 첫 번째만 사용한다.
  result[key] = child;
} else {
  result.rest.push(child);
}

// 4. JSX에 작성한 순서 대신, 부모가 정한 화면 위치에 배치한다.
{slots.threadHeader ?? <ThreadHeader />}
{slots.sidebarFooter}
{slots.rest}
```

주의 
- 직접 자식으로 선언해야 하는 이유 : 현재 `extractSlots()`는 `Children.forEach(children, ...)`로 자식을 순회하지만 자식의 `props.children`을 재귀 탐색하지 않는다.  
- `useMemo`는 `children` 참조가 바뀌면 슬롯 분류를 다시 계산하도록 캐시한다. 슬롯을 식별하는 기준은 컴포넌트 이름 문자열이나 실제 DOM 태그가 아니라 **React 요소의 `type` 참조**다. `AgentInterface.ThreadHeader`가 동일한 `ThreadHeader`를 참조하므로 Map에서 찾을 수 있다.



## Open UI Lang 사전 지식 

- $로 시작하는 변수는 상태(State) 변수입니다.
- @로 시작하는 함수는 내장 표현식/액션 함수입니다 (@Set, @Clamp, @Each, @Includes, @Toggle, @CopyToClipboard 등).
  - @Set은 상태 변수의 값을 바꾸는 내장 액션 이다.  
- 대문자로 시작하는 함수(Col, Row, Grid, Card, Title, Text, Badge, Button 등)는 UI 컴포넌트입니다.
- 일반 변수는 접두사 없이 그냥 사용하면 된다.  
- Call expression : 대문자 시작하는 이름 + 괄호 형태, eg, Col(..), @Each(..)


@Set은 상태 변수의 값을 바꾸는 내장 액션입니다.
```
root = Col([Button("실행", @Set($result, @Pick(["A","B","C"]))), Text($result == null ? "null" : "결과: " + $result)])
$result = null
---
@Set($result, @Pick(["A","B","C"]))
     └ 대상   └ 새로 저장할 값

이 예제는 다음 순서로 동작합니다.

1. 처음에는 $result = null이므로 화면에 "null"이 표시됩니다.
2. 실행 버튼을 누르면 @Pick(["A","B","C"])가 하나를 뽑습니다.
3. @Set이 뽑은 값을 $result에 저장합니다.
4. $result를 읽는 Text(...)가 갱신됩니다.
```


### 렌더러와 런타임의 내부 처리 로직 (실제 라이브러리 기반 간소화)

OpenUI는 **(1) 평가(Evaluation) 단계 (`@openuidev/lang-core`)**와 **(2) 렌더링(Rendering) 단계 (`@openuidev/react-lang`)**의 2단계로 동작합니다.

#### 1단계: AST 평가 단계 (`evaluate` in `@openuidev/lang-core`)
코드 파싱 후 만들어진 AST 노드를 순회하며 상태, 변수, 함수, 액션, 컴포넌트 호출을 각각 알맞은 값으로 평가합니다.

```typescript
function evaluate(node, context) {
  switch (node.k) {
    // ① 상태 변수 ($guests, $got 등)
    case "StateRef":
      return context.getState(node.n);

    // ② 일반 변수 참조 (lines, ingredients, head 등)
    case "Ref":
    case "RuntimeRef":
      return context.resolveRef(node.n);

    // ③ @내장함수, @액션, 커스텀 함수 (@Each, @Clamp, @Set 등)
    case "Comp": {
      // 1) 내장/커스텀 함수 (@Each, @Format, @Clamp 등): 즉시 실행해 결과값 반환
      if (context.functions[node.name]) {
        return callFunction(node.name, node.args, context);
      }
      // 2) 액션 (@Set, @Toggle, @CopyToClipboard 등): 클릭 시 실행될 액션 플랜({ steps: [...] }) 반환
      if (context.actions[node.name]) {
        return createActionPlan(node.name, node.args, context);
      }
      // 3) UI 컴포넌트 (Col, Card, Button 등): props를 평가한 뒤 ElementNode 반환
      return {
        type: "element",
        typeName: node.name, // "Card", "Col" 등
        props: evaluateProps(node.args, context),
        statementId: node.statementId,
      };
    }

    // ④ 데이터 구조 및 리터럴 (배열, 객체, 문자열, 숫자 등)
    case "Arr": return node.els.map(el => evaluate(el, context));
    case "Obj": return Object.fromEntries(node.entries.map(([k, v]) => [k, evaluate(v, context)]));
    case "Str": case "Num": case "Bool": return node.v;
    case "Null": return null;
  }
}
```

#### 2단계: React 렌더링 단계 (`renderDeep` in `@openuidev/react-lang`)
평가된 결과 트리에서 **UI 컴포넌트(`type === "element"`)**와 **일반 데이터(`lines`, `string`, `number` 등)**를 구별하여 React 화면을 그립니다.

```tsx
function renderDeep(value) {
  if (value == null) return null;

  // ① 일반 문자열/숫자/불리언 -> 텍스트로 바로 출력
  if (typeof value === "string") return value;
  if (typeof value === "number" || typeof value === "boolean") return String(value);

  // ② 배열 -> 자식 요소들을 재귀적으로 렌더링
  if (Array.isArray(value)) {
    return value.map((v, i) => <Fragment key={i}>{renderDeep(v)}</Fragment>);
  }

  // ③ UI 컴포넌트 객체 -> 라이브러리에 등록된 실제 React 컴포넌트로 렌더링
  if (typeof value === "object" && value !== null) {
    if (value.type === "element") {
      const Comp = library.components[value.typeName]?.component;
      if (!Comp) return null;
      return <Comp props={value.props} renderNode={renderDeep} />;
    }
  }

  // ④ 그 외 일반 순수 데이터 객체 (lines의 { name, amount } 등)
  // UI 노드가 아니므로 화면에 그리지 않고 무시(null) 처리 (참조 데이터로만 쓰임)
  return null;
}
```

## 한계점 및 운영에서 고려 사항 

1. OpenUI 응답을 일반 텍스트로 요약하면 구조 정보가 손실될 위험  

2. Autofix: 생성 완료 후 유효하지 않은 OpenUI Lang 코드를 단 한 번의 API 호출로 자동 수정(Repair). 기존 모델 공급자, 추론 환경, 에이전트 프레임워크를 그대로 유지한 채 적용 가능하다.

3. 신뢰성 모니터링 (Reliability Monitoring): 생성된 인터페이스의 실패율, 반복되는 에러 유형, 실패 원인이 된 생성 내역을 추적·분석. Gateway/Autofix 사용 시 자동 활성화되며, 자체 추론 환경에서는 Observability SDK를 통해 연동할 수 있다.


4. 플링킹 이슈 및 validator failover 이슈 (오픈소스의 프리미엄 영역은 모니터링 부분임.)  

5. LangGraph JS 예제에는 LLM이 만든 OpenUI Lang을 서버에서 검증하고, 오류를 모델에 돌려보내 수정시키는 단계는 없다.( Gateway 쪽에서 검증·보정을 맡는 구조 - 돈내라 )
- 모델이 잘못된 UI 크기를 출력한 사례는 검증이 가능할지 모르겠다.? width, height가 나온것은 validator 통과. 그러나 적절한 높이 너비가 아니라면 화면에서 꺠질 수 있음  


6. 렌더링 성능에 대해서 측정 할 필요가 있음
